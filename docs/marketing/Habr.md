Агенту, который генерирует и оценивает кандидатов, всё равно нужна стратегия поиска. Следует ли ему улучшать

лучший результат, пробовать другую ветку, запускать несколько попыток параллельно или остановиться? Такие решения

часто оказываются разбросаны по циклу повторных попыток.

Dream-RSI SDK выносит эту стратегию за Python-интерфейс. Вы предоставляете агента поиска и

оценщик. SDK записывает процесс исследования в виде дерева, позволяет политикам воспроизводить записанные результаты

и может попросить модель-разработчика написать новый исполняемый код политики на основе обратной связи из replay.

Текущая версия — `0.1.0a2`. У неё нет обязательных сторонних зависимостей времени выполнения,

и она требует Python 3.11 или новее. Это альфа-версия, поэтому начните с небольшой задачи.

### Сначала запустите цикл пошагового улучшения с оценкой

Установите пакет в виртуальное окружение:

```bash

python -m pip install dreamrsi==0.1.0a2

```

Сохраните следующий код как `first_run.py`:

```python

from dreamrsi import Budget, DreamRSI, FunctionalAgentAdapter

from dreamrsi.policies import DepthFirstPolicy

def refine(state):

return {"x": state["x"] / 2}

rsi = DreamRSI(

adapter=FunctionalAgentAdapter(refine),

evaluator=lambda candidate: -(candidate["x"] \*\* 2),

policy=DepthFirstPolicy(),

budget=Budget(model_calls=6),

)

result = rsi.run_sync({"x": 8.0})

print(result.best)

print(result.best_score)

print(result.costs.model_calls)

```

Запустите `python first_run.py`. Ожидаемый лучший кандидат — `{'x': 0.125}`, его оценка —

`-0.015625`, а выполнение использует шесть вызовов агента. Этот намеренно простой пример показывает, как

состояние передаётся между итерациями улучшения. Он не демонстрирует, что LLM становится более способной.

Отрицательная квадратичная ошибка здесь важна: оценки максимизируются, поэтому превращение ошибки в отрицательное

значение позволяет выразить задачу минимизации. В вашем адаптере состояние может содержать ответ,

программу-кандидат или набор параметров. Ваш оценщик должен измерять что-то действительно полезное.

### Затем сравните политики на записанном опыте

В репозитории есть `examples/02_replay_lab.py`, который записывает игрушечный процесс поиска и воспроизводит

несколько политик. После клонирования репозитория и его установки запустите этот пример. Он выводит

количество дополнительных вызовов агента поиска и оценщика во время replay: оба значения должны быть равны нулю.

Это полезная граница. Вы можете исследовать альтернативное поведение при поиске, не заставляя

агента поиска заново воспроизводить каждый уже известный результат. Replay всё равно выполняет локальные вычисления

и не может предсказывать результаты за пределами записанного дерева. Это свидетельства из конечной истории, а не оракул.

### Где здесь используется локальная LLM

Стандартный оптимизатор ищет по параметрам встроенных политик. Чтобы создавать новый исполняемый исходный код,

используйте `LLMPolicyDeveloper` вместе с клиентом вашей модели. Программа-кандидат интерпретируется, оценивается

на обучающем replay и получает обратную связь для следующей итерации. Для продвижения политики можно потребовать

отдельные проверочные среды перед следующим онлайн-запуском.

В репозитории есть локальный эксперимент с Bonsai, включая неудачные ревизии и

сериализованные артефакты политики. Он демонстрирует этот механизм на игрушечной задаче. Он не

доказывает общих улучшений производительности, и вам не нужно загружать эту модель, чтобы попробовать

базовую интеграцию выше.

Если у вас уже есть цикл generate/evaluate/refine, следующий полезный шаг довольно прост: запустите этот

пример, а затем замените функцию улучшения и оценщик одной задачей, которую вы хорошо понимаете.

Если состояние включает активные браузерные сессии, файлы или базы данных, сначала прочитайте контракт

интеграции рабочего пространства, прежде чем считать такое состояние безопасно копируемым.

[Краткое руководство и replay lab](https://github.com/TheAstrayDev/dream-rsi-sdk#quickstart).

Если интеграция не работает, [опишите структуру задачи и первое возникшее препятствие](https://github.com/TheAstrayDev/dream-rsi-sdk/issues/new?template=early_adopter.yml).

## Статья B — Локальная LLM переписала политику поиска: самым полезным оказалась обратная связь из replay

*Раскрытие информации: эта статья была подготовлена при помощи ИИ с использованием архивных отчётов проекта.

Я независимо поддерживаю Dream-RSI SDK; это не продукт Google и не официальная репродукция.*

Другой исходный файл — это ещё не обязательно другой алгоритм. Это различие стало

важным во время тестирования локальной модели в качестве разработчика политик для Dream-RSI SDK.

В эксперименте небольшой агент поиска оставался неизменным: на каждой итерации улучшения он делил число пополам.

Оценщик предпочитал значения, расположенные ближе к нулю. Bonsai-27B-Q1_0, запущенная локально через

llama.cpp, писала код, который решал, какие из уже раскрытых ветвей расширять и когда останавливаться.

Это игрушечная задача, но она позволяет рассмотреть все движущиеся части. LLM пишет логику исследования;

она не отвечает на задачу напрямую и не изменяет собственные веса.

### Шесть ревизий, включая неудачную

В финальном дополнительном эксперименте было запрошено шесть ревизий исходного кода. Пять получили корректные оценки replay.

Шестая завершилась с ошибкой и осталась в архивном отчёте без выдуманной оценки.

| Ревизия | Оценка replay ↑ | Пробы | Раунды принятия решений |

| --- | ---: | ---: | ---: |

| 1 | -1.050000 | 6 | 3 |

| 2 | -1.049975 | 5 | 1000 |

| 3 | -1.043750 | 5 | 4 |

| 4, выбрана | -1.026250 | 3 | 4 |

| 5 | -1.026250 | 3 | 4 |

| 6 | Ошибка | — | — |

Ревизия 2 показывает, почему одной итоговой оценки недостаточно. Она использовала меньше проб, чем

базовый вариант, но потратила 997 раундов без новых наблюдений. Выполнение завершилось

из-за ограничения replay по количеству раундов.

После обратной связи об этом поведении модель переписала логику остановки; ревизия 3 завершилась

за четыре раунда. В ревизии 4 изменился выбор ветвей, и потребовалось три пробы.

Контракт обратной связи включал предыдущий исходный код, измеренные траектории, компоненты оценки,

ошибки и причинную информацию о последнем выполненном раунде. Политика могла определить, что

предыдущее продолжение ничего не раскрыло, при этом не получая скрытые будущие результаты.

### Выбор политики не был финальным тестом

Выбранный исходный код прошёл replay в трёх отдельных проверочных средах. Он был сериализован,

повторно загружен с сохранением хеша исходного кода и запущен на новом начальном значении. При шести

вызовах агента поиска каждый базовый вариант достиг остатка 1.5, а сгенерированная политика —

0.1875: снижение остатка в этой задаче на 87.5%.

Это не означает снижение расходов на LLM на 87.5%. Модель-разработчик выполняла собственные

запросы, а replay также потреблял вычислительные ресурсы. Это также не означает, что обобщающая способность доказана:

обучение, проверка и новая задача были масштабированными версиями одной и той же задачи деления пополам.

### Почему более ранние запуски всё ещё важны

В более ранней матрице из трёх seed-значений только один из трёх seed прошёл продвижение, при этом оценку получили

семь ревизий из двенадцати. Эксперимент не прошёл более строгий критерий разнообразия поведения. В более позднем

дополнительном запуске после этих неудач были изменены обратная связь и настройки рассуждения. Его следует описывать

именно как дополнительный эксперимент, а не незаметно подменять им показатель успеха контролируемого запуска с несколькими seed.

Для меня полезный инженерный результат здесь — полная цепочка доказательств: исходный код, написанный моделью,

измеренные изменения поведения, исправление логики остановки, валидация, продвижение и выполнение после

повторной загрузки. Следующий вопрос — даст ли этот подход ощутимые улучшения на более сложных задачах.

Если вы хотите изучить эту цепочку, начните с

[отчёта, необработанных артефактов и графика](https://github.com/TheAstrayDev/dream-rsi-sdk/blob/main/docs/experiments/sandbox-v4-2026-09-22.md).

Если у вас есть более сложная задача пошагового улучшения с оценкой, минимальный воспроизводимый пример будет

гораздо более ценной обратной связью, чем звезда на GitHub или абстрактный прогноз о рекурсивном самоулучшении.
